## 1. システムビジョン

### 1.1 全体目標

現行 PoC は「動くプロトタイプ」として whisper.cpp (base/medium) + Ollama qwen2.5-coder による日本語会議録音システムを確立した。しかし実運用環境（物流倉庫・市場・店舗）では SNR（信号対雑音比）が著しく低く、標準 Whisper モデルの CER（文字誤り率）は英語の 2〜3 倍に達することが判明している。

次世代システムの目標を以下の3軸で定義する。

**軸1: 日本語 ASR 精度の根本的改善**
- 現状: medium モデルで業務音声 CER 推定 15〜25%（騒音環境）
- 目標: CER 8% 以下（静音オフィス）、15% 以下（騒音フィールド）
- アプローチ: 日本語特化蒸留モデル (Kotoba-Whisper) + 前処理ノイズ除去

**軸2: モバイル・オフライン優先アーキテクチャ**
- 現状: PC 上のサーバーに依存。iPad/スマホからネットワーク越しに接続
- 目標: iPad 単体でのオンデバイス推論（WhisperKit + Core ML）。ネットワーク不要
- アプローチ: オフラインファースト設計、クラウドフォールバックはオプション

**軸3: エンドツーエンドのレイテンシ改善**
- 現状: リアルタイムチャンク処理 2〜5秒/チャンク; 最終転写 medium: 30〜120秒/30分音声
- 目標: リアルタイムプレビュー < 2秒/チャンク; 最終議事録生成 < 60秒/30分音声
- アプローチ: 蒸留モデルの軽量化、量子化 (Q5_K_M)

### 1.2 対象ユーザーと展開環境

| ユーザー種別 | デバイス | ネットワーク | 騒音レベル | 主要な課題 |
|---|---|---|---|---|
| 営業担当（商談会議） | iPad / MacBook | 安定（社内 WiFi） | 低〜中 | 固有名詞の誤認識（得意先名・商品名） |
| フィールド担当（倉庫・市場） | iPad / Android タブレット | 不安定 / オフライン | 高（フォークリフト・搬送音） | SNR 低下による CER 急増、接続断 |
| 店舗スタッフ（小売店） | スマートフォン | 4G/LTE（不安定） | 中〜高（BGM・呼び込み） | バッテリー制限、処理速度 |

### 1.3 精度目標

```
CER（文字誤り率）= (S + D + I) / N
  S: 置換エラー数, D: 削除エラー数, I: 挿入エラー数, N: 正解文字数
```

| フェーズ | 対象モデル | 静音オフィス | 騒音フィールド |
|---|---|---|---|
| 現在 (PoC) | ggml-medium | ~15% | ~25%+ |
| Phase 1 後 | Kotoba-Whisper v2 + RNNoise | 8% | 15% |
| Phase 2 後 | Kotoba-Whisper + 話者分離 | 6% | 12% |
| Phase 3 後 | WhisperKit (iOS Core ML) | 5% | 10% |
| Phase 4 後 | LoRA ファインチューニング済み | 3% | 8% |

## 2. 技術スタック比較

### 2.1 ASR エンジン4候補の詳細評価

#### A. whisper.cpp + Kotoba-Whisper GGML（推奨・主軸）

- **概要**: OpenAI Whisper-large-v3 を日本語音声データで知識蒸留したモデルファミリー。GGML 形式が公式サポートされており、既存 whisper.cpp パイプラインへの差し替えが最小コストで実現できる
- **GitHub**: https://github.com/kotoba-tech/kotoba-whisper
- **精度**: ReazonSpeech テストセットで large-v3 と同等以上の日本語 CER。日本語会話コーパス（CSJ・ReazonSpeech・JSUT）での蒸留により標準 Whisper より誤認識が少ない
- **モデルサイズ**: FP16: ~1.6GB / Q5_K_M 量子化後: ~950MB（現行 medium の ~1.5GB より軽量）
- **モバイル互換性**: WhisperKit 経由で iOS Core ML 変換可能。Android は whisper.cpp NDK ビルドで動作
- **ストリーミング**: 既存 whisper-server の `/inference` エンドポイントでそのまま動作
- **ライセンス**: Apache 2.0（商用利用可）
- **移行コスト**: **最小（モデルファイル差し替えのみ）**

#### B. Qwen3-ASR-0.6B / 1.7B（将来候補・ストリーミング特化）

- **概要**: Alibaba Cloud が公開した ASR 特化 LLM。Qwen3 アーキテクチャに音声エンコーダーを統合。streaming モードを公式サポート
- **GitHub**: https://github.com/QwenLM/Qwen-Audio
- **精度**: 日本語 CommonVoice で CER ~4〜6%（静音環境）。LLM ベースのため文脈理解が高く、同音異義語の誤変換が少ない傾向
- **モデルサイズ**: 0.6B GGUF Q4: ~400MB / 1.7B GGUF Q4: ~1.0GB
- **モバイル互換性**: GGUF 形式での llama.cpp 経由推論が可能。WhisperKit との統合は 2026年4月時点で発展途上
- **ストリーミング**: ネイティブ対応。ただし既存 whisper-server API 非互換のため新規エンドポイント実装が必要
- **ライセンス**: Qwen License（月間 1億 MAU 超で Alibaba 事前承認必要）
- **移行コスト**: 中〜高

#### C. ReazonSpeech-k2-v2（高精度・サーバー専用）

- **概要**: 日本最大の日本語音声コーパス（~35,000 時間）で訓練した k2/Icefall ベースの ASR。Conformer + Transducer アーキテクチャ
- **GitHub**: https://github.com/reazon-research/ReazonSpeech
- **精度**: CER ~3〜5%（現時点で日本語 OSS ASR 最高水準）。方言・口語への対応が比較的強い
- **モバイル互換性**: iOS/Android への直接デプロイは困難。サーバーサイド専用として運用が現実的
- **ストリーミング**: k2 Transducer がネイティブ対応。ただし既存 API と非互換
- **ライセンス**: Apache 2.0
- **移行コスト**: 高（k2/Icefall ランタイム導入、既存 API 非互換）

#### D. Vosk small-ja（超軽量・デバイス制約環境向け）

- **概要**: Kaldi ベースのオフライン音声認識。iOS / Android ネイティブライブラリが成熟
- **ダウンロード**: https://alphacephei.com/vosk/models/vosk-model-small-ja-0.22.zip （48MB）
- **精度**: small-ja CER ~12〜18%（静音）。騒音環境では ~25%+ に悪化する可能性
- **モバイル互換性**: iOS Swift バインディング・Android 公式 AAR ライブラリが提供済み
- **ストリーミング**: ネイティブ対応（最低レイテンシ ~200ms）
- **ライセンス**: Apache 2.0
- **移行コスト**: 高（Python vosk ライブラリ導入、既存 whisper.cpp 非互換）

### 2.2 エンジン比較マトリクス

| 評価軸 | Kotoba-Whisper | Qwen3-ASR-1.7B | ReazonSpeech-k2 | Vosk small-ja |
|---|---|---|---|---|
| 静音 CER（推定） | ~7% | ~4% | ~3% | ~15% |
| 騒音 CER（推定） | ~12% | ~10% | ~9% | ~25% |
| モデルサイズ（量子化後） | ~950MB | ~1.0GB | ~800MB | 48MB |
| iOS 対応 | WhisperKit Core ML | 発展途上 | 非対応 | Swift バインディング |
| Android 対応 | NDK ビルド | llama.cpp | PyTorch Mobile | 公式 AAR |
| 既存 PoC 移行コスト | **最小** | 中〜高 | 高 | 高 |
| ライセンス | Apache 2.0 | Qwen License | Apache 2.0 | Apache 2.0 |
| ストリーミング | チャンク処理 | ネイティブ | ネイティブ | ネイティブ |

**推奨方針**: 短期は Kotoba-Whisper（移行コスト最小・実績あり）。中期は Qwen3-ASR または ReazonSpeech-k2-v2 をサーバー高精度レーンに追加する2レーン構成。

### 3.2 Stage 2 ノイズ除去の詳細

**RNNoise の採用根拠**
- WebRTC Opus コーデックに内蔵された RNN ベースのノイズ抑制
- モデルサイズ: ~100KB（ブラウザ WASM 動作可）
- リアルタイム処理: 10ms フレーム単位
- GitHub: https://github.com/xiph/rnnoise

**ffmpeg サーバー側フォールバック**
```bash
# サーバー側ノイズ除去（iOS Safari 非対応時・Android 非対応時のフォールバック）
ffmpeg -i input.webm -af "arnndn=m=cb.rnnn" -ar 16000 -ac 1 -c:a pcm_s16le output.wav
```

**ノイズ除去強度の環境変数制御**
```
NOISE_REDUCTION_LEVEL=none      # 無効（デバッグ用）
NOISE_REDUCTION_LEVEL=mild      # 軽度（オフィス環境）
NOISE_REDUCTION_LEVEL=moderate  # 中程度（店舗・市場、デフォルト）
NOISE_REDUCTION_LEVEL=aggressive # 強度（倉庫・工場）
```

### 3.3 Stage 3 VAD 保守的設定の根拠

**既存 PoC での実証済み知見**（`work/poc/backend/services/transcription.py` の設計コメントより）:

> Silero-VAD のデフォルト閾値（0.5）は、日本語の「間（ま）」や短い発話（「はい」「ええ」「そうですね」など）を無音として誤判定する。これにより短い肯定応答が消えるだけでなく、直後の発話冒頭が切れてデコーダーが幻覚フレーズを生成する原因になる。

**閾値 0.35 の選定理由**:
- 0.5 以上: 日本語短発話を過剰カット（既存 PoC で実証）
- 0.35 前後: 倉庫環境の背景ノイズと音声の境界として実測的に適切
- 0.2 以下: ノイズを音声として拾いすぎる

### 3.4 Stage 6 LLM 後処理の設計原則

**コンマ区切り語彙リスト禁止の原則（必須遵守）**

Whisper デコーダーの `--prompt` にコンマ区切りの単語リストを渡すと、デコーダーが "リストの続き" を生成しようとして精度が大幅に低下することが実験で確認されている。

```python
# NG: デコーダーを混乱させる
--prompt "成約率,フォロー,アポ,見積もり"

# OK: 自然文として渡す
--prompt "成約率の確認とフォローアップについて、アポイントメントと見積もりの進捗を話し合う会議"
```

**OOM 防止のための1回呼び出し原則（必須遵守）**

8.7GB RAM 環境では whisper-cli 実行中（~1.5GB）と Ollama 推論（~1.0GB）が直列実行で合計 ~5.3GB のピークを形成する。これを並列化したり2回に分割すると RAM ピークが 6〜7GB を超えスワップが発生する。

```python
# NG: 2回呼び出し（OOM リスク）
corrected = ollama_call(raw_transcript, mode="correction")
summary = ollama_call(corrected, mode="summary")

# OK: 1回の呼び出しで補正+構造化を統合
corrected, summary = ollama_call(raw_transcript, mode="combined")
```

**WhisperKit の位置付け**
- GitHub: https://github.com/argmaxinc/WhisperKit

- iOS 17+ / macOS 14+ 対応。iPad Pro (M シリーズ) では Neural Engine を活用

**Kotoba-Whisper の Core ML 変換**
```bash

    --model-version kotoba-tech/kotoba-whisper-v2.2 \

```

**Progressive Enhancement（段階的機能強化）**

```
Level 0 — オフライン完全動作（必須）
  WhisperKit (Core ML) → ローカル SQLite 保存 → UI 表示

Level 1 — ネットワーク有時の LLM 補完
  WhisperKit → 基本テキスト → サーバー Ollama で後処理
  ※ 低帯域時はテキストのみ送信: ~1KB/分 vs 音声 ~1MB/分

Level 2 — サーバー高精度再転写（WiFi 接続時）
  音声を Opus 24kbps 圧縮 → サーバー Kotoba Q5_K_M で再転写
  会議終了後・WiFi 接続時に非同期実行
```

**iOS アプリ主要コンポーネント**

```
AudioCapture.swift       — AVAudioEngine → 16kHz PCM バッファ
NoiseReduction.swift     — AVAudioUnitEQ or RNNoise Swift ラッパー
WhisperKitTranscriber.swift — WhisperKit(modelFolder: "kotoba-whisper-v2.2")

LLMPostProcessor.swift   — オフライン時: llama.swift (qwen3:1.7b)
                           オンライン時: FastAPI /api/recordings へ POST
SyncManager.swift        — ネットワーク復帰検知 → 未同期データをサーバーへ送信
MeetingRecordView.swift  — SwiftUI UI + ローカル GRDB.swift
```

### 6.1 業界別語彙テンプレート（即時実施可能）

`work/poc/backend/services/vocabulary.py`（新規作成）として業種別語彙を管理する。

```python
VOCAB_TEMPLATES = {
    "logistics": (
        "入荷、出荷、ピッキング、仕分け、棚卸し、ロット番号、SKU、"
        "フォークリフト、パレット、荷主、発注、受注残、在庫回転率、WMS"
    ),
    "retail": (
        "売場、発注点、欠品、棚割り、陳列、回転率、POS、定番、"
        "エンド、フェイス数、バイヤー、MD、売上高、プランオグラム"
    ),
    "sales": (
        "成約率、フォローアップ、アポイントメント、見積もり、提案書、"
        "発注、受注、母数、進捗管理、商談、得意先、クロージング、競合"
    ),
}

def build_initial_prompt(
    meeting_type: str,
    client_name: str = "",
    owner_name: str = "",
    industry: str = "sales",
) -> str:
    """whisper の --prompt 用の自然文を生成する。
    注意: コンマ区切りワードリストは使用しない（デコーダー混乱の原因）。
    上限: ~224 トークン（日本語換算 ~200 文字）。
    """
    vocab = VOCAB_TEMPLATES.get(industry, VOCAB_TEMPLATES["sales"])
    parts = [p for p in [client_name, owner_name, vocab] if p]
    return "、".join(parts)[:200]
```

### 6.2 LoRA ファインチューニングパイプライン（Phase 4）

**ターゲット誤認識パターン**（現行 PoC の LLM プロンプトから抽出）:
- カタカナ→漢字誤変換: フォロー→鼓動、アポ→アハ、フィード→不意打ち
- 同音異字: 成約→奠約、先週→前週、母数→ハハ数
- 物流特有: ロット番号・棚番・入荷区分の認識失敗

**訓練パイプライン**

```
Step 1: データ収集
  顧客録音音声（実際の会議・現場訪問）: 最低 2〜5 時間推奨
  手動テキスト正解ラベル付け（Whisper Medium の出力を人間が修正）
  形式: JSON Lines {audio: wav_path, text: correct_text}

Step 2: LoRA 訓練（PEFT + Transformers）
  ベースモデル: kotoba-tech/kotoba-whisper-v2.2 (HuggingFace 形式)
  LoRA 設定: rank=16, alpha=32, dropout=0.05
  ターゲット層: q_proj, v_proj（エンコーダー + デコーダー）
  GPU 推奨: Google Colab T4（無料枠）で実施可能
  CPU 訓練: 可能だが 2時間音声 × 3エポック で ~10〜20時間かかる

Step 3: GGML 変換
  LoRA ウェイト → マージ → HuggingFace 形式
  models/convert-hf-to-ggml.py で GGML に変換
  出力: models/ggml-kotoba-finetuned.bin

Step 4: CER 検証
  テストセットで CER 計測（ベースモデルとの比較）
  合格基準: ターゲット語彙の誤認識率が 50% 以上改善
```

### 6.3 訓練データ収集フロー

```
会議録音
    ↓
ASR 転写（Kotoba-Whisper）
    ↓
LLM 補正（qwen3:1.7b）
    ↓

    ↓ （データが 2時間以上蓄積されたタイミングで）

```

**データ管理の最小要件**:
- 精度改善効果が出始めるデータ量: ~1〜2 時間の音声 + 正解テキスト
- LoRA 再訓練サイクル: 月次推奨
